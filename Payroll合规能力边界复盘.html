成品 Payroll vs 白标 Payroll：合规能力边界

为什么我们误以为"系统会自动合规"，Salsa / Check 到底兜不兜，下一步怎么走。

结论先行

  1. Check 不做任何的 OT 计算，但 Salsa 能够计算 OT，以及多角色多费率的 OT。
  2. Salsa 不做最低工资是否合规的校验，Check 也不做，主流软件只有 Toast 自动做，ADP 需要安装插件。
  3. Check 的 Tip Credit 只是提供字段，具体金额的计算仍需接入的平台自行计算。
  4. 大部分 Payroll 系统都无法支持加州的一系列特殊规定，比如：split shift、餐歇休息额外工资。需要老板手动添加到 Payroll。
  5. 没有一个 Payroll 系统能够 100% 保证最低工资合规，在合约条款中会写明此类合规由餐厅老板承担。

1. 我们误解了什么？

我们默认——只要接了 payroll 系统，"把钱发对"相关的合规它会自动兜底。具体有两点想当然：

  • 最低工资校验：以为系统会自动检查"发的工资是否达到当地最低工资"、不够会提醒或补差。
  • 额外应付工资 / 罚时（premium pay）：以为系统会自动处理加州餐休/间歇罚时、分段班、报到时间工资这类"该多给的钱"。

——我们以为这些 Salsa 会默认支持。

2. 今日信息更新

上述两点，Salsa 都不支持（均已向 Salsa 确认 / 有文档依据）：

  • 不支持最低工资校验：Salsa 明确回复——不校验、不提醒、不拦截；低于最低工资的一批照算照确认，无任何警告。补差也要我们自己算好当 pay item 传。
  • 不支持额外应付工资 / 罚时：Salsa 的 Premium Pay 目前仅支持纽约（分段班、工时跨度、工资平价），且非 NY 地点直接返回 HTTP 400。加州餐休罚时等完全没有。
结论：这两块合规能力，需要由接入的平台（Chowbus）自建——在设时薪、跑薪之前，在我们自己产品里把住。

3. 为什么会误判？根本原因

根因是：没有事先搞清"成品 payroll"和"白标 payroll"的能力边界。

成品会兜、白标上交给平台：

  • 成品 / 全服务（ADP、QuickBooks、Paychex、Toast 等）：把最低工资、小费补差、罚时这些做进了自己产品——因为它们端到端拥有整条产品和客户。但"做进产品"程度不一：餐厅垂直的 Toast 开箱自动，通用的 ADP/QuickBooks 要配置或手动（详见第 4 节对比）。
  • Salsa、Check（白标 / 嵌入式 payroll）：是"引擎 / 管道"，刻意把这类能力上交给接入的平台去处理——只负责算税、发钱、报税。
旁证：同类平台 Homebase、7shifts 用的也是白标引擎，最低工资 / 小费补差 / 罚时都是它们自己建在产品里的——"平台自建"是这条路线的常态，不是个例。

而我们之前想当然了：

  • 因为对 payroll 不够了解，以为"白标也会兜底所有合规"；
  • 但白标从未承诺过——它们功能集 / 宣传里的 "compliance" 其实只指税务合规（代扣、缴税、申报），不含最低工资、加班底线、罚时这类"工资工时合规"；
  • "compliance" 被笼统当成"全部合规"，卖方只兑现了税那部分——同一个词，买卖双方理解不一致。
教训：评估任何 payroll，要把"合规"拆成税务合规（成品 / 白标通常都做）和工资工时合规（白标基本不做、需平台自建），并直接问对方"你们不做什么、要我们建什么"，而不是只问"你们能做什么"。

5. 下一步计划

路线 A 接 Salsa

需要我们自建/补齐的能力：

  • ① 最低工资校验 + 提示补差（设时薪时校验；每期算补差，作为 pay item 传）；
  • ② 全部额外应付工资/罚时——尤其加州餐休罚时（Salsa 完全不支持，检测+计算全自建）；
  • ③ 加州"固定薪资非豁免"加班的正确算法，需与 Salsa 确认如何手工配置公式。

路线 B 接 Check

接 Check 与接 Salsa 要自建的几乎一样：

  • ① 最低工资校验 + 补差：仍需自建（Check 不做）；
  • ② 加州休息罚时：仍需自建——Check 只给 API 字段（regular rate·独立行），漏餐检测和计算还是我们做；
  • ③ Tip credit：仍需自建——只给专门字段、不代算（此项 Check 略强：Salsa 明年才有字段）；
  • ④ 加班：Check 也不自动——加班小时/费率要平台自己传，Check 只按 rate×hours 出金额、且不支持加权加班；此项 Salsa 反而自动算（含多费率）。
小结：Check 相比 Salsa 几乎没有"少自建"——最低工资、休息罚时、加班的检测与计算，接哪家都要 Chowbus 自建。Check 唯一略强是 tip credit 已有专门字段（但仍不代算）。

路线 C 不接白标，直接对接 ADP / QuickBooks（成品）

  • 好处：罚时、加班州特例等合规大多由它们兜底，平台自建相对少。
  • 代价：失去白标 / 嵌入 Chowbus 的体验和控制权——客户会感知到是"另一个系统"，这是重大产品路线取舍。
要拍板的决策：①要不要接 Salsa？②若接 Salsa/Check，上面的自建清单进不进本期范围、投入多少？③是否值得为"少自建合规"而放弃白标、转投成品(ADP/QuickBooks)？——建议结合"客户州分布（加州占比）+ 有多少全服务正餐 + 白标对品牌的重要性"一起权衡。
